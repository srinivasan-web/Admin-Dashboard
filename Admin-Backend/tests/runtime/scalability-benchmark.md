# Isolated MySQL scalability benchmark

These scripts are **not** part of the normal test suite. They have not been run against a million-row database in this workspace. Do not point them at a production, shared, or valuable database.

1. Provision a new, empty MySQL database named `durafit_bench_<run_id>` with a dedicated account. Configure the backend to use it with `APP_ENV=testing` and `DB_CONNECTION=mysql`. Run the project's migrations there **only after checking the exact database name**. The seeder will refuse nonempty domain tables and a name outside this prefix; it never drops or truncates tables.
2. Set `DURAFIT_BENCHMARK_CONFIRM=seed-isolated-mysql`, then run `php tests/runtime/seed-scalability-staging.php --rows=1000000 --batch=200`. The script inserts one million products, stock balances, specifications, orders, order items, reservations, and movements, plus two million price-history rows. It reports seed elapsed time and product-row throughput. Use a smaller `--rows` only to smoke-test the script; the measurement script requires at least one million products and orders.
3. Run `php tests/runtime/benchmark-scalability-staging.php --samples=20` on that same database. Add `--analyze` only when bounded `EXPLAIN ANALYZE SELECT` is acceptable. The report includes p50/p95/p99 sequential query timings, query throughput, session handler-read deltas, JSON plans, and approximate table/index bytes. Run the existing `tests/runtime/profile-public-api.php --samples=20 --explain` separately for Laravel endpoint timings.
4. Record the database version, host/storage, PHP runtime, cache/OPcache settings, concurrency, error rate, and p95/p99 for actual HTTP traffic. Use a separate load generator to test concurrent browsing, orders, payment transitions, and inventory changes; these scripts do **not** measure lock waits or concurrent write throughput. Capture MySQL Performance Schema lock/deadlock data during that run. Do not compare optimized and baseline results from different datasets or hosts.

The fixture intentionally skews half of products into one category and distributes the remainder across ten categories and five warehouses. It models one active reservation/movement per order and twenty distinct specification values. This is synthetic, not a production distribution; vary skew, order size, history depth, and active/inactive ratios before making index or capacity decisions. Index changes should be trialed on a separate cloned benchmark database and compared for both reads and seed/write throughput.
